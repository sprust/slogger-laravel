# SLogger Laravel

[English](README.md) | **Русский**

SLogger Laravel — пакет трейсинга/наблюдаемости (observability) для Laravel-приложений. Он записывает трейсы запросов/команд/джобов/событий и т.д. и доставляет их на удалённый бэкенд через настраиваемые диспатчеры.

Этот README описывает установку, конфигурацию, вотчеры, маскирование, диспатчеры и сценарии использования.

## Требования

- PHP >= 8.2
- Laravel 10.26+ (протестировано на 10, 11 и 12)
- Драйвер очередей для диспатчера `queue` и запущенный на нём воркер очереди

## Установка

1) Установите пакет (через Composer в вашем приложении):

```bash
composer require slogger/laravel
```

2) Опубликуйте конфиг:

```bash
php artisan vendor:publish --tag=slogger-laravel
```

3) Настройте env и `config/slogger.php` (см. ниже).

## Быстрый старт

Включите и используйте диспатчер `queue`:

```dotenv
SLOGGER_ENABLED=true
SLOGGER_TOKEN=your-api-token
SLOGGER_DISPATCHER=queue
SLOGGER_DISPATCHER_QUEUE_CONNECTION=redis
SLOGGER_DISPATCHER_QUEUE_NAME=slogger
SLOGGER_DISPATCHER_QUEUE_SOCKET_CLIENT_URL=tcp://your-slogger-host:port
SLOGGER_LOG_REQUESTS_ENABLED=true
```

Добавьте middleware к роутам, которые нужно трейсить (см. [Middleware](#middleware)), затем
запустите воркер очереди на этом коннекшене и очереди:

```bash
php artisan queue:work redis --queue=slogger
```

## Бэкенд сбора трейсов

SLogger Laravel отправляет трейсы в отдельный бэкенд-сервис. Референсный проект бэкенда:

```text
https://github.com/sprust/slogger
```

Используйте его инструкции по установке, чтобы развернуть сервер и настроить URL/токен API-клиента в этом пакете.

### Свой бэкенд / клиент

Бэкенд можно заменить собственным API-клиентом: забиндьте свою реализацию
`SLoggerLaravel\Dispatcher\ApiClients\ApiClientInterface` (один метод,
`sendTraces(TracesObject $traces): void`) в сервис-провайдере вашего приложения. Или
унаследуйте `ApiClientFactory` — это `readonly`-класс, так что наследник тоже должен быть
`readonly`, — и забиндьте наследника вместо него. Клиент используется только джобой
`SendTracesJob` диспатчера `queue`; из коробки `SLOGGER_DISPATCHER_QUEUE_API_CLIENT`
принимает только `socket`.

## Конфигурация

Вся конфигурация находится в `config/slogger.php` с переопределением через env. Ключевые секции:

### Общее

```dotenv
SLOGGER_ENABLED=false
SLOGGER_TOKEN=
SLOGGER_TRACE_ID_PREFIX=
SLOGGER_LOG_CHANNEL=daily
SLOGGER_CONTEXT=array
```

- `SLOGGER_ENABLED`: глобальное включение/выключение всего трейсинга.
- `SLOGGER_TOKEN`: API-токен для диспатчеров.
- `SLOGGER_TRACE_ID_PREFIX`: свой префикс для trace ID. Если пустой — используется slug от `app.name` или `app`.
- `SLOGGER_LOG_CHANNEL`: канал для внутренних ошибок пакета.
- `SLOGGER_CONTEXT`: где хранится состояние одной единицы работы — `array`, если вы не ведёте
  несколько запросов или джоб одновременно в одном процессе. См. [Конкурентность](#конкурентность).

### Диспатчеры

```dotenv
SLOGGER_DISPATCHER=queue
SLOGGER_DISPATCHER_QUEUE_CONNECTION=slogger-rabbitmq
SLOGGER_DISPATCHER_QUEUE_NAME=slogger
SLOGGER_DISPATCHER_QUEUE_API_CLIENT=socket
SLOGGER_DISPATCHER_QUEUE_SOCKET_CLIENT_URL=tcp://0.0.0.0:0002
SLOGGER_DISPATCHER_QUEUE_SOCKET_CLIENT_TIMEOUT=10
```

- `SLOGGER_DISPATCHER`: `queue` или `memory`.
- Диспатчер `queue` кладёт трейсы в очередь; ваши воркеры очереди отправляют их через socket-клиент.
- Диспатчер `memory` хранит трейсы в памяти (удобно для тестов/разработки).
- `SLOGGER_DISPATCHER_QUEUE_API_CLIENT`: клиент, через который отправляет джоба, —
  `socket`, единственный поставляемый.
- `SLOGGER_DISPATCHER_QUEUE_SOCKET_CLIENT_URL`: адрес приёмника; значения по умолчанию
  нет.

`SLOGGER_DISPATCHER_QUEUE_CONNECTION` **обязателен** для диспатчера `queue` — фолбэка на
`QUEUE_CONNECTION` нет намеренно: телеметрия не должна молча делить queue-коннекшен с
приложением. Используйте выделенный коннекшен.

`SLOGGER_DISPATCHER_QUEUE_SOCKET_CLIENT_TIMEOUT` — таймаут чтения/записи socket-клиента в
секундах (по умолчанию `10`). Он даёт запас, когда приёмник перегружен и подтверждение реально
задерживается; таймаут установки соединения — отдельный и остаётся 2 секунды.

Если приёмник закрыл соединение (рестарт, деплой, сетевой сбой), клиент это замечает и
переподключается прозрачно — ровно одна повторная попытка на батч. Таймауты так **не**
ретраятся: это превратило бы перегруженный приёмник в шторм переподключений — их обрабатывает
политика ретраев джобы ниже.

Ретраи отправки зафиксированы намеренно: 5 попыток с паузами 5/10/30/60 секунд между ними.
После исчерпания попыток батч **дропается** с rate-limited предупреждением в лог-канале
SLogger — отправка, упавшая внутри джобы, никогда не попадает в `failed_jobs`. Туда Laravel
всё ещё может записать только сбой на стороне воркера — таймаут воркера, воркер, убитый
посреди попытки.

Неудачная попытка не доходит до exception handler приложения: джоба сама возвращает себя в
очередь с нужной паузой, а не выбрасывает исключение — воркер репортит всё, что вылетело из
`handle()`, на каждой попытке, и рестарт приёмника превращался в тысячи ошибок в мониторинге
хост-приложения. Исключение — `sync`-соединение: там нет следующей попытки, и ошибка
пробрасывается как раньше.

### Заголовок родительского трейса запроса

```dotenv
SLOGGER_REQUESTS_HEADER_PARENT_TRACE_ID_KEY=x-parent-trace-id
```

Связывает трейсы между сервисами через один заголовок:

- **входящий запрос**: его значение становится родителем трейса запроса;
- **ответ**: middleware ставит собственный trace id этого запроса на возвращаемый ответ,
  так что клиент его действительно получает (раньше он ставился в `terminate()`, который
  под FPM выполняется уже после отправки ответа);
- **исходящий вызов HTTP-клиента**: несёт trace id самого вызова, так что вызываемый
  сервис вешает свой трейс под этот вызов.

Пустое значение выключает все три.

### Вотчеры (включение/выключение)

Все вотчеры по умолчанию выключены. Родительские — запросы, джобы, команды — открывают
трейс; остальные пишут только внутри открытого (исключение — событие из списка
`can_be_orphan` вотчера событий).

```dotenv
SLOGGER_LOG_COMMANDS_ENABLED=true
SLOGGER_LOG_JOBS_ENABLED=true
SLOGGER_LOG_REQUESTS_ENABLED=true
SLOGGER_LOG_CACHE_ENABLED=true
SLOGGER_LOG_DATABASE_ENABLED=true
SLOGGER_LOG_DUMP_ENABLED=true
SLOGGER_LOG_EVENT_ENABLED=true
SLOGGER_LOG_GATE_ENABLED=true
SLOGGER_LOG_HTTP_ENABLED=true
SLOGGER_LOG_LOG_ENABLED=true
SLOGGER_LOG_MAIL_ENABLED=true
SLOGGER_LOG_MODEL_ENABLED=true
SLOGGER_LOG_NOTIFICATION_ENABLED=true
SLOGGER_LOG_SCHEDULE_ENABLED=true
```

### Прочие настройки

Задаются только в `config/slogger.php`:

- `watchers.*.config.excepted` (вотчеры команд и джоб): команды и классы джоб, которые не
  трейсятся. Для команд по умолчанию это `queue:work`, `queue:listen`, `horizon:work` и
  `schedule:run`; для джоб — `SendTracesJob`, чтобы отправка батча не становилась
  отдельным трейсом.
- Вотчер событий: `only_events` (записывать только эти; пусто — все), `ignore_events`
  (поверх встроенных `Illuminate\*`, `Laravel\*`, `eloquent*`, `SLoggerLaravel\*` и ещё
  нескольких, которые действуют, пока `only_events` пуст), `serialize_events` (классы
  событий, чей JSON попадает в трейс) и `can_be_orphan` (записываются, даже когда ни один
  трейс не открыт). Имена — маски `Str::is`, кроме `serialize_events`, где нужны точные
  имена классов.
- `data_completer.excluded_file_masks`: файлы, которые пропускаются при поиске места
  вызова для `__trace` (маски `Str::is`), — для ваших собственных обёрток вокруг
  трейсируемых вызовов.
- `listeners`: слушатели событий, которые регистрирует пакет; по умолчанию
  `WatcherErrorEvent` уходит в `report()`, так что сбой вотчера попадает в ваш обработчик
  ошибок, а не в запрос.

## Что записывает SLogger

Каждый трейс содержит:
- `trace_id`, `parent_trace_id`, `type`, `status`, `tags`
- `data` (данные конкретного вотчера, плюс `__trace` — место вызова — и `__add`, значения,
  добавленные через `TraceDataComplementer::add()`)
- `duration`, `memory`, `cpu`, `logged_at`
- при создании: является ли он родительским трейсом — таким, который получит обновление
  при закрытии, — и id процесса, который его создал

`memory` — это процент использования `memory_limit`, и он **null, когда лимита нет**
(`memory_limit = -1`, дефолт CLI): процентом быть не от чего. `cpu` — минутный load
average в процентах от мощности машины, нормированный на число ядер; на перегруженной
машине может быть больше 100; он null там, где число ядер не прочитать (нет
`/proc/cpuinfo`, то есть вне Linux).

Основные данные вотчеров:
- `request`: `uri` (шаблон маршрута, `/reset/{token}`; путь без маршрута обрезается до
  первого сегмента), ip_address, method, action, middlewares, query/query_string,
  route_parameters, boot_time, `request.headers`/`request.parameters`,
  `response.status`/`headers`/`data` (тело, когда запрос принимает JSON или ответ — XML,
  иначе цель редиректа или view)
- `command`: command, arguments, options, exit_code
- `job`: connection_name, `job` (name, class, max_tries, timeout, backoff, data, ...), status (`processed`, `failed`, `released_after_exception`, `timed_out`, `exception_occurred`), exception.
  Трейсятся только джобы, отправленные в очередь, пока пакет включён
- `event`: слушатели, broadcast, опционально сериализованный payload
- `model`: действие, класс модели, ключ, изменения
- `mail`: mailable/notification, queued, `message` (from/reply_to/to/cc/bcc парами `email`/`full_name`, тема)
- `notification`: notification, notifiable, channel, queued, `recipients`, response
- `cache`: type (`hit`, `missed`, `set`, `forget`), key и `cache.<key>` (value, tags,
  expiration). Значение, которое маскеру слишком длинно читать, записывается вместо этого
  как `{"__skipped": "value_too_large"}`
- `database`: connection, sql (до 10 000 символов), bindings; время запроса — это
  `duration` трейса. Биндинг вотчер маскирует сам, по длине: строка длиннее пяти символов
  становится `********`, более короткая, int или float остаются как есть
- `http-client`: method, uri, query/query_string, `request.headers`/`payload`,
  `response.status_code`/`headers`/`body`, exception, тайминги соединения в `transfer` (параллельные
  запросы трейсятся независимо, так что `Http::pool()` работает). Трейсятся только
  клиенты, собранные с хендлером из раздела [Трейсинг Guzzle / HTTP-клиента](#трейсинг-guzzle--http-клиента)
- `schedule`: command, description, expression, timezone, user, output (читается до
  предела маскера)
- `dump`: dump; `log`: level, message, context; `gate`: ability, result, user_id, arguments

Воркер очереди завершает job по таймауту из обработчика `SIGALRM`, то есть посреди работы
job, и сразу после этого убивает себя. Трейсы, открытые внутри job и ещё не закрытые к
этому моменту, закрываются со статусом `failed` и тегом `__interrupted`, сохраняя уже
собранные данные; job, отправленный на повтор вместо `failed`, закрывается по событию
`JobTimedOut`. Трейс всё ещё может остаться в статусе `started`, если сигнал придёт во
время отправки трейса в диспетчер — там трейсинг приостановлен, и события таймаута
теряются, — или если воркер убит сигналом, который он не обрабатывает.

## Запросы

### Middleware

Для трейсинга HTTP-запросов добавьте middleware к нужным роутам:

```php
\SLoggerLaravel\Middleware\HttpMiddleware::class
```

### Конфиг вотчера запросов

`config/slogger.php`:

```php
'watchers' => [
    [
        'class'   => \SLoggerLaravel\Watchers\Parents\RequestWatcher::class,
        'enabled' => env('SLOGGER_LOG_REQUESTS_ENABLED', false),
        'config'  => [
            // log only matched paths (optional)
            'only_paths' => [
                // 'api/*',
            ],

            // skip matched paths
            'excepted_paths' => [
                // 'health',
            ],

            'input' => [
                // apply input formatting only for these paths
                'only_paths' => [
                    // 'api/*',
                ],

                // hide all request params for these paths
                'hidden_paths' => [
                    '*',
                ],

                // above this the parameters are not recorded at all (bytes)
                'max_content_length' => 1000000,
            ],

            'output' => [
                // apply response formatting only for these paths
                'only_paths' => [
                    // 'api/*',
                ],

                // hide all response data for these paths
                'hidden_paths' => [
                    '*',
                ],

                // the same for the response body (bytes)
                'max_content_length' => 1000000,
            ],
        ],
    ],
],
```

#### `only_paths`
- `only_paths` (верхний уровень): логировать только совпавшие пути запросов.
- `input.only_paths`: применять форматирование входных данных только к совпавшим путям (остальные вычищаются).
- `output.only_paths`: применять форматирование ответа только к совпавшим путям (остальные вычищаются).

Паттерны сопоставляются через Laravel `Str::is`.

Поставляемые `hidden_paths` — это `['*']`: параметры запроса и данные ответа везде
записываются как `{"__cleaned": null}`, пока вы не сузите список до путей, которые должны
оставаться скрытыми.

### Тела запросов и ответов

Тело, которое не JSON, но **является XML-документом** — SOAP-конверт, XML-API, — кладётся
как сам документ, под ключом `__xml`:

```json
{"__xml": "<order><api_token>********</api_token></order>"}
```

А не как массив, полученный из него: так теряются атрибуты, повторяющиеся элементы и
неймспейсы, а трейс, который больше не совпадает с описываемым документом, стоит немного.
Маскер заглядывает внутрь такой строки (см. «Правила маскирования»), поэтому документ
маскируется на месте. Работает в обе стороны и у обоих вотчеров: входящее тело запроса,
которое Laravel не разбирает в `input()`, исходящее тело и оба ответа.

**Отправитель должен сам это сказать.** Тело записывается как XML, только если его
`Content-Type` — XML-ный (`application/xml`, `text/xml`, `application/soap+xml`, `*+xml`)
**и** оно похоже на документ: начинается с `<`, а его первые 512 байт — не HTML-страница.
На этом этапе ничего не разбирается. Одной разметки мало: HTML-фрагмент — то, чем отвечает
htmx- или Turbo-эндпоинт, — это валидная разметка с CSRF-токеном в `value="…"`, а маскер
сверяет *имена* и до него не дотянется. Тело, которое ни JSON, ни помеченное как XML,
отбрасывается, как и раньше.

XML-тело, которое не является валидным UTF-8, записывается как
`{"__skipped": "non_utf8_body"}`: данные трейса сериализуются через `json_encode`, и битые
байты заменили бы весь пейлоад этого трейса ошибкой кодировки, а не только тело.

Тела больше `max_content_length` (по умолчанию 1 000 000 байт) не записываются:

| Вотчер | Маркер |
| --- | --- |
| request: параметры | `{"__skipped": "request_too_large"}` |
| request: ответ | `{"__skipped": "response_too_large"}` |
| http-client | `{"__cleaned": "--cleaned:big-size-<bytes>--"}` |
| любой, сверх того, что читает маскер (1 МБ) | `{"__skipped": "body_too_large"}` |

Последний появляется, только если собственный лимит вотчера выставлен больше 1 МБ. Вотчер
http-client также пишет `{"__skipped": "non_seekable_body"}` для потока, который нельзя
перемотать.

## Правила маскирования

Маскирование выполняется **в джобе диспетчера**, прямо перед отправкой батча, и никогда
не выполняется в отслеживаемом приложении. Приложение платит только за сбор данных и
передачу их дальше; обход пейлоада ключ за ключом оплачивают воркеры очереди. Отсюда
два следствия:

- **В очереди лежат незамаскированные данные трейсов.** Всё, что собрали вотчеры, лежит
  в хранилище очереди до момента отправки, поэтому очередь slogger настолько же
  чувствительна, как и сами трейсы: выделите ей своё подключение, держите короткое
  время хранения и не давайте упавшим батчам копиться в `failed_jobs`.
- Диспетчер `memory` не маскирует — у него нет джобы. Это средство для разработки и
  тестов, никуда наружу он ничего не отправляет.

Вотчеры не маскируют. В рантайме они только скрывают и урезают: `only_paths`,
`excepted_paths`, `hidden_paths`, `max_content_length`, списки `excepted` у вотчеров.
Единственное исключение — вотчер базы: биндинги позиционные, никакой список ключей до них
не дотянется, и джобе-диспетчеру решать не по чему. Вотчер маскирует их сам, по длине:
строка длиннее пяти символов становится `********`, более короткая, int и float пишутся
как были. По биндингу не понять, пароль это или номер страницы, так что короткий или числовой
секрет — PIN, OTP, номер карты в виде числа — до приёмника доедет. Не держите такое в
открытых колонках, либо выключайте вотчер.

```php
        'authentication',
        'authorization',
        'oauth',
        'passwd',
        'pass',
        'passcode',
        'passphrase',
        'pw',
        // not bare `signed`: it would take `signed_at` and `signed_by` too

        'signed_request',
        'signed_url',
        'private',
        'privatekey',
        'session',
        'sessionid',
        'csrf',
        'jwt',
        'bearer',
        'otp',
        'totp',
        'cvv',
        'cvc',
        'pin',
        'pincode',
        'iban',

        '*apikey*',
        '*api-key*',
        '*credential*',
        '*cookie*',
        '*signature*',
        '*session_id*',
        '*card_number*',
        '*recovery_code*',
    ],

    // two characters kept at each end, so two records still look different.
    // these identify a person rather than authenticate one - never a secret here.
    //
    // no bare `name`: it is matched as a word component, and `job.name` holds a
    // job class, `listeners[].name` a listener class, a file's `name` its filename
    'partial_keys' => [
        'username',
        'user_name',
        'nickname',
        'surname',
        'middlename',
        'middle_name',
        'fullname',
        'full_name',

        '*email*',
        '*phone*',
        '*recipient*',
        '*firstname*',
        '*first_name*',
        '*lastname*',
        '*last_name*',
    ],

    // matched against the value and masked in place, for what no key name points
    // at - an address in a log line. an invalid pattern is ignored, not fatal.
    //
    // order matters: each pattern runs on what the previous ones left, so narrow
    // before broad. a capture group masks the group and keeps the rest.
    'value_patterns' => [
        // postgres://app:secret@db. a scheme is required, so `//assets:v2@2x.png`
        // is left alone; the group runs to the last `@`
        'url_credentials' => '/\b[a-z][a-z0-9+.-]*:\/\/[^\/\s:@]+:([^\/\s]+)@/i',

        // a secret in a url, wherever it turns up. the parameter name is a word,
        // not a substring: unbounded, it took `?author=` and `?country_code=`
        'url_secret' => '/[?&](?:[\w.-]*[_-])?(?:token|apikey|api_key|api-key|secret|password|passwd|auth|authorization|signature|credential|session|sessionid)(?:[_-][\w.-]*)?=([^&\s"\'<>]+)/i',

        // whole parameter name only, or it takes `country_code` and `zip_code`
        'url_oauth_code' => '/[?&]code=([^&\s"\'<>]+)/i',

        'email' => '/[\w.+-]+@[\w-]+\.[\w.-]*[\w-]/u',
    ],
],
```

Оба списка — это **маски**, без учёта регистра, где `*` — подстановочный знак. Маска
сверяется с ключом целиком **и с каждым его словом-компонентом**: ключ разбивается по
любому символу, который не буква и не цифра (`_`, `-`, `.`, `:`, `/`, пробел, ...), и
по границам camelCase:

| Маска | Подходит | Не подходит |
| --- | --- | --- |
| `pass` | `pass`, `db_pass`, `smtp_pass`, `pass_hash` | `passengers`, `compass`, `bypass_cache` |
| `auth` | `auth`, `basic_auth`, `x-auth-user`, `php-auth-pw` | `author`, `authorized` |
| `token` | `token`, `api_token`, `apiToken` | `tokenizer` |
| `*token*` | `api_token`, `tokenizer` | `stock` |

Ни поиск подстроки, ни сверка с ключом целиком по отдельности не годятся. Подстрочное
правило нельзя сузить, когда оно оказалось слишком широким: `auth` подходил и к
`author`, и каждое совпадение забирало значение целиком, а с ним и всё поддерево. А
сверку с ключом целиком нельзя расширить, не вернув ложные срабатывания звёздочками:
`auth` тогда перестал подходить к `php-auth-pw` — открытому паролю, который Symfony
кладёт рядом с base64-заголовком. Сверка по компонентам даёт и то, и другое, а маска со
звёздочками остаётся для имён, состоящих из одного слова.

Совпадение на родительском ключе распространяется на всё поддерево: `auth` покрывает и
`auth.method` — родитель при этом должен быть уровнем ниже верхнего, потому что верхний
уровень не сверяется вовсе (см. ниже). Ключ, попавший в оба списка, маскируется целиком:
строгий список побеждает.

Маскирование выключено, только когда пусты все три списка, включая `value_patterns`.
На биндинги вотчера БД этот выключатель не распространяется: они позиционные, никакой
список ключей не скажет, который из них пароль, поэтому вотчер маскирует их сам, по
длине, что бы ни лежало в этих списках.

Разделение — это и есть суть. Секрет обесценивается от любой утечки, поэтому
`masking.full_keys` заменяет значение полностью: `********`, фиксированной ширины, чтобы не
утекла ещё и длина секрета. Адрес, телефон или имя нужны в основном чтобы различать
записи, поэтому `masking.partial_keys` сохраняет по два символа с каждого края:
`john.doe@example.com` превращается в `jo****************om`; значение короче шести
символов превращается в столько же `*`, сколько в нём символов. **Никогда не кладите
секрет в `partial_keys`**: оставшегося хватит, чтобы связывать записи между собой, а для
короткого значения — чтобы его угадать.

Значение, которое является **строкой с документом**, разбирается, маскируется и
запаковывается обратно: приложения передают целые документы строками — каст `array` у
Eloquent кладёт такой прямо в изменения модели, SOAP-вызов приезжает целиком, — а ключ,
под которым лежит эта строка, ничего не говорит о её содержимом. Разбираются три
формата:

- **JSON** — строки, которые и открываются, и закрываются как документ: `{`…`}` или
  `[`…`]`, так что проза, начинающаяся с `{`, остаётся прозой. При переупаковке
  нормализуется экранирование, а число, слишком большое или слишком точное для float в
  PHP, теряет точность. Документ, который открывается как документ и не читается —
  NDJSON, сырой control-символ, глубже, чем берёт `json_decode`, — маскируется
  **целиком**: его никто не прочитал, значит за него никто не ручается.
- **XML** — строки, которые разбираются как XML. Имена элементов и атрибутов сверяются
  так же, как ключи объекта, совпадение покрывает поддерево (`<auth>` маскирует всё
  внутри), namespace-префикс имя не прячет (`soap:Envelope` сверяется по `Envelope`),
  CDATA маскируется на месте, а к комментариям и processing-инструкциям применяются
  паттерны значений. При пересборке может нормализоваться незначимый пробельный
  материал и кавычки атрибутов; документ, у которого не было XML-декларации, её не
  получит.
- **Родная сериализация PHP** — строки, начинающиеся с `a:<n>:{`. Сессия, лежащая в
  кеше, — как раз такая: в ней CSRF-токен и хеш пароля под ключами, которые списки
  ловят. Объекты при чтении никогда не создаются, а блоб с сериализованным объектом
  или обратной ссылкой не разбирается вовсе: первый без своего класса не собрать
  обратно, второй разворачивается в массив, содержащий сам себя. Оба достаются
  value-паттернам, которые видят их как обычные строки.

Документ, в котором **ничего** не совпало, остаётся байт в байт.

Какой бы ни была форма, обход останавливается на фиксированной глубине и маскирует
остаток целиком. Это страховка, а не лимит, до которого кто-то должен доходить:
кончившаяся память — фатальная ошибка, а фатальная ошибка в джобе диспетчера уносит с
собой воркер.

**Трейс, который маскер не смог прочитать, заменяется, а не дропается и не уезжает
как есть.** Его `data` становится единственным ключом `__mask_error` с описанием
поломки. Маскирование детерминированное, поэтому выпущенное наружу исключение стоило
бы всего батча и каждого его ретрая — вместе с трейсами вокруг сломанного.

XML-сущности не разворачиваются никогда, поэтому документ, приехавший снаружи, не
заставит диспетчер прочитать локальный файл или развернуть billion-laughs-бомбу во время
маскирования — маскирование идёт в воркере над пейлоадами, которые писало не приложение.
Отсюда два следствия, и оба падают в **закрытую** сторону: документ, значения которого
живут во внутреннем DTD, маскируется целиком, потому что маска вокруг `&secret;` при
живом объявлении читается как защита, ею не являясь; и документ с объявлениями, который
вообще не разобрался, маскируется целиком по той же причине.

Всё остальное, что просто начинается с `<` — кусок текста, страница, — не трогается, к
нему применяются только паттерны значений, как к обычному тексту.

Значение под ключом **`query_string`** маскируется параметр за параметром, а не целиком:
из `page=2&api_token=secret` останется страница и пропадёт токен. Именно туда вотчеры
запросов кладут query-строку url: url — это ещё и тег, и заголовок, до которых не
дотягивается ни один список ключей — только паттерны значений, а до заголовка не дотягиваются даже они.

### Паттерны значений

Некоторые вещи опознаются по собственной форме, где бы они ни оказались, и ни один ключ
на них не указывает: адрес внутри `Anonymous:mail,john@example.com` или посреди
лог-сообщения. `masking.value_patterns` — это регулярки, которые сверяются со
**значением**, а найденное маскируется по месту, так что остальная строка остаётся
читаемой: группа захвата заменяется на `********`, паттерн без неё маскирует частично:

```
'invoice sent to john.doe@example.com'  ->  'invoice sent to jo****************om'
```

Они не привязаны к ключу, поэтому, в отличие от списков ключей, работают и на первом
уровне, достают внутрь JSON-строк и query-строк, в **ключи массивов** и в **теги**
трейса — которые больше ничто не маскирует. Совпадение по ключу всё равно главнее: у `token` с адресом внутри не останется ничего, а не только
середина. Некорректная регулярка просто отбрасывается, а не сыплет warning'ами на каждой
строке каждого трейса.

Списки ключей и паттерны закрывают разное и рассчитаны на совместную работу: `*phone*`
в `partial_keys` ловит телефон под `customer.phone`, который никакой адресный паттерн не
увидит.

Помните, где кончается первый уровень (см. ниже): `recipients` у вотчера уведомлений *и
есть* первый уровень, поэтому до него достают только паттерны значений — адрес там
маскируется, а телефон под `recipients.vonage` — нет.

**Первый уровень `data` трейса не маскируется никогда.** Этот уровень принадлежит
вотчеру, а не приложению: `connection_name`, `request`, `changes`, `context`, `bindings`
и прочее — фиксированная структура, а отслеживаемые данные начинаются уровнем ниже.
Поэтому сверка начинается внутри неё: `context.customer_email` и
`job.data.customer_email` маскируются, а `recipients` у вотчера уведомлений остаётся
нетронутым, хотя `*recipient*` есть в `partial_keys`. Вотчеры, у которых на первом уровне лежали данные приложения, были
переделаны, чтобы правило работало и для них: значение кеша лежит под своим кеш-ключом
(`cache.<key>.value` — и тогда список сверяется именно с ключом), а почтовые адреса — под
`message` парами `email`/`full_name`.

Расширяйте маску, если поставляемый список не покрывает что-то ваше — `*ssn*` вместо
`ssn`, `*iban*` вместо `iban`, — и сужайте, если под неё попало нужное поле. Для
телеметрии перестраховка безопаснее недосмотра, но это выбор, который вы делаете
для каждой маски, а не решение за вас.

### Куда список ключей не дотягивается

Некоторые поля — свободный текст, и никакое имя ключа не описывает, что внутри. Списки
ключей на них не действуют; работают только `value_patterns`, и только для того, у чего
есть узнаваемая форма:

| Поле | Что внутри |
| --- | --- |
| `log.message` | то, что залогировали |
| `dump.dump` | то, что дампнули, — `dd($user->api_token)` это ровно оно |
| `schedule.output` | stdout запланированной команды |
| `db.sql` и sql-фрагмент в тегах трейса `db` | сам запрос, хотя значения едут биндингами, а их вотчер маскирует по длине |

Здесь средства — вотчерские: выключить вотчер или не класть секреты в то, что логируете
и дампите. **Теги** трейса в том же положении — голые строки, которые никакой ключ не
называет, — поэтому паттерны значений применяются и к ним.

### Замаскированные значения

Замаскированные значения сохраняют базовые типы, поэтому замаскированный пейлоад
остаётся той же формы, что и исходный:
- `null` -> `null`
- `bool` -> `false`
- `int` -> `0`
- `float` -> `0.0`
- `string` -> `********`, либо по два символа с каждого края при частичной маске (одни `*`,
  если символов меньше шести)
- строка длиннее того, что читает маскер (1 МБ) -> `********`, какой бы ни был ключ
- объект -> то, во что его превратил бы `json_encode`, и дальше он обходится как
  обычный массив (объект с `__toString()` вместо этого маскируется как своя строка).
  `********` он становится, только если обходить нечего — нет публичного состояния
  или его нечем закодировать

Пустая строка остаётся как есть: маска на её месте утверждала бы, что там что-то было.

**Массив обходится, а не заменяется.** Подошедший ключ покрывает поддерево, поэтому
маскируется каждый *лист* под ним, а структура и имена ключей остаются:
`{"token":{"a":"secret","b":2}}` превращается в `{"token":{"a":"********","b":0}}`. Ключи
— тоже данные, когда их выбирает приложение (кеш-ключ сплошь и рядом выглядит как
`otp:<адрес>`), поэтому `value_patterns` применяются и к ключам массивов, и к тегам —
двум местам, куда список ключей не дотягивается.

## Трейсинг Guzzle / HTTP-клиента

Хендлер SLogger можно подключить к Guzzle:

```php
new \GuzzleHttp\Client([
    'base_uri' => 'https://url.com',
    'handler'  => app(\SLoggerLaravel\Guzzle\GuzzleHandlerFactory::class)->prepareHandler(
        (new \SLoggerLaravel\RequestPreparer\RequestDataFormatters())
            ->add(
                new \SLoggerLaravel\RequestPreparer\RequestDataFormatter(
                    urlPatterns: ['*/api/auth/*', '*sensitive/some/*'],
                    hideAllRequestParameters: true,
                    hideAllResponseData: true
                )
            )
    ),
])
```

Паттерны сверяются с **полным url** — со схемой, хостом и query-строкой, — поэтому
паттерну пути нужна ведущая `*`. `prepareHandler()` принимает существующий
`HandlerStack` вторым аргументом и возвращает стек нетронутым, пока вотчер http-client
выключен.

Форматтеры только скрывают; тело от 1 МБ заменяет вотчер, а чувствительные значения
маскируются позже, в джобе диспетчера.

### Тайминги соединения

Когда вызов идёт через curl (дефолтный хендлер Guzzle), трейс несёт то, что curl
намерил, в `transfer` — и для упавшего вызова тоже, так что сервер, принявший соединение
и так и не ответивший, отличим от сервера, до которого не достучались:

```json
"transfer": {
    "namelookup_time": 0.001234,
    "connect_time": 0.021,
    "appconnect_time": 0.063,
    "pretransfer_time": 0.0631,
    "starttransfer_time": 0.25,
    "total_time": 0.3,
    "primary_ip": "93.184.216.34"
}
```

Времена — в секундах и **накопительные от начала вызова**, как их отдаёт curl: каждое
включает все предыдущие фазы.

| Поле | Что это |
|---|---|
| `namelookup_time` | DNS-резолв завершён |
| `connect_time` | TCP-соединение с сервером установлено — время соединения, включая DNS |
| `appconnect_time` | TLS-рукопожатие завершено (`0` по обычному http) |
| `pretransfer_time` | всё готово, запрос начал отправляться |
| `starttransfer_time` | пришёл первый байт ответа (TTFB) |
| `total_time` | вызов завершён целиком |
| `primary_ip` | IP-адрес, к которому реально подключились |

Время одной фазы — разница соседних полей: например, по https TLS занял
`appconnect_time - connect_time`, а сервер думал `starttransfer_time - pretransfer_time`.

- **Переиспользованное соединение даёт `0`.** Keep-alive соединение, взятое из пула curl,
  заново не резолвилось и не соединялось, поэтому `namelookup_time` и `connect_time`
  равны `0` — это не ошибка замера.
- **Нет curl — нет `transfer`.** Stream-хендлер и мок не отдают статистики хендлера, и
  ключ не пишется вовсе, а не заполняется нулями.

Тайминги приходят через опцию Guzzle `on_stats`. Ваш собственный `on_stats` — или тот,
что ставит `Http`-клиент Laravel, чтобы заполнить `$response->transferStats`, —
по-прежнему вызывается.

## Конкурентность

Пока трейс идёт, у него есть состояние: какой трейс сейчас родитель, какие родительские
трейсы ещё открыты, приостановлены ли вотчеры, что `add()` сказал про этот запрос. Там,
где процесс обрабатывает один запрос, одну джобу или одну команду за раз, это состояние
процесса, и держать его в свойствах нескольких синглтонов — правильно.

Под рантаймом, который ведёт несколько единиц работы одновременно в одном процессе —
корутины, event loop, файберы — свойство общее для всех. Второй запрос читает id первого
и вкладывается под него; запрос внутри приостановленной секции заглушает вотчеры всех
остальных запросов в полёте; `user_id` одного запроса попадает в трейсы другого.

Поэтому состояние живёт в хранилище, а хранилище решает, что значит «текущая».

### Выбор хранилища

```dotenv
# array (default) | fiber | App\Tracing\YourStore
SLOGGER_CONTEXT=array
```

- **`array`** — одна карта на весь процесс: то, что делали все предыдущие версии, и
  верный ответ для php-fpm, `artisan` и `queue:work`. Стоит по умолчанию, поэтому
  обновление ничего не меняет.
- **`fiber`** держит карту на каждый работающий `Fiber` и одну общую, когда файберов нет.
  Ставьте, если ваш рантайм даёт каждому запросу или каждой джобе **свой PHP-файбер**.
- **всё остальное** считается именем класса вашего собственного хранилища: класса,
  реализующего `TraceContextInterface`, который резолвится из контейнера. Всё прочее
  падает с `Unknown trace context`. Пока `SLOGGER_ENABLED` выключен, настройка не
  читается.

**Прежде чем ставить `fiber`, проверьте, что он вам подходит.** Он различает единицы
работы по `Fiber::getCurrent()`, поэтому под рантаймом, чьи корутины — не PHP-файберы
(Swoole или планировщик вне PHP), он молча вырождается в `array` и ничего не чинит.
Одна строка внутри запроса всё решает:

```php
Log::debug('slogger: in a fiber?', ['yes' => Fiber::getCurrent() !== null]);
```

Если там `false` — пишите своё хранилище.

### Своё хранилище

Два метода и никаких зависимостей:

```php
namespace App\Tracing;

use SLoggerLaravel\Context\TraceContextInterface;

class CoroutineTraceContext implements TraceContextInterface
{
    public function get(string $key, mixed $default = null): mixed { /* ... */ }

    public function set(string $key, mixed $value): void { /* ... */ }
}
```

Дальше `SLOGGER_CONTEXT=App\Tracing\CoroutineTraceContext`. Четыре вещи, которые оно
обязано соблюдать:

- **Хранилище — синглтон и само не держит состояния.** Оно определяет, куда смотреть, на
  каждом вызове. Вотчеры строятся один раз на бутстрапе и навсегда сохраняют полученные
  объекты, поэтому хранилище, выбравшее себе область видимости в конструкторе, так и
  будет отвечать за ту единицу работы, которая его построила.
- **Ключ со значением `null` — это не отсутствующий ключ.** `get()` должен вернуть `null`
  для первого и дефолт только для второго. Запись `$value ?? $default` их склеивает, а
  «родительского трейса нет» записывается именно как `null`.
- **Запись должна действительно записывать.** Если у нижележащего контекста есть режим
  «не заменять существующий ключ» — не используйте его: хранилище, молча сохраняющее
  первое записанное в ключ значение, воспроизводит ровно тот баг, ради которого всё это
  делалось.
- **Значения должны возвращаться по значению.** Всё, что здесь лежит, — массивы скаляров
  и экземпляры `Carbon`, а пакет клонирует `Carbon` перед тем, как сохранить или изменить
  его, так что отдать единице работы поверхностную копию массива достаточно, — но
  хранилище, отдающее двум единицам один и тот же изменяемый объект, снова делает их
  состояние общим.

Убрать ключ намеренно нельзя. Хранилище, чьё чтение проваливается к объемлющей единице
работы (у корутинного контекста с наследованием обычно так и есть), открыло бы значение
объемлющей единицы; «здесь ничего нет» записывается как `null` или как пустой список.

### Чего `fiber` не делает

Чтение не проваливается к файберу, который создал текущий. PHP не может сказать, какой
это был файбер, а догадка — это как раз то, как несвязанные трейсы сшиваются в одно
дерево.

Последствие стоит знать до переключения: **файбер, запущенный внутри трассируемого
запроса, начинает без собственного состояния, поэтому дочерние трейсы, отправленные
изнутри него, теряются** — у запроса, лога или события, записанного там, нет открытого
родительского трейса в этом файбере, и `push()` выходит сразу. Родительские трейсы,
начатые там, записываются, но корневыми, а не вложенными в запрос; так же записывается и
всё, что вотчер помечает как способное стоять само по себе (`can_be_orphan`). Если код
вашего приложения запускает файберы *внутри* единицы работы (amphp/revolt и всё, что на
них), `fiber` будет стоить вам этой телеметрии; хранилище, умеющее назвать объемлющую
корутину, — не будет.

То же касается исходящего HTTP-вызова, ответ на который обрабатывается не там, где вызов
был сделан. Хук ответа Guzzle исполняется там, где промис разрешается: с curl и `wait()`
это тот же файбер, что делал вызов, и всё работает, — но под рантаймом, который разрешает
промисы в собственном файбере цикла, вызов открывается в одной единице работы, а ответ
приходит в другой, и трейс не закрывается никогда. Дело не в том, в какой карте вотчер
держит запись: собственный учёт вызова у процессора всё равно живёт с той единицей,
которая его сделала.

### Единица работы, которая не отчиталась

Любое хранилище, привязывающее состояние к единице работы — это или ваше собственное, —
меняет то, что происходит, когда единица заканчивается молча. Стоит знать до
переключения.

Исключение — не этот случай: фреймворк всё равно фиксирует `RequestHandled`, `JobFailed`
или `CommandFinished`, трейс закрывается как упавший, и всё нижесказанное неважно. Речь
про единицу, **брошенную приостановленной**: планировщик убил, сработал таймаут, процесс
завершается.

Ничего из того, что держит хранилище, не течёт. Состояние уходит вместе с единицей: PHP
разматывает стек уничтоженного файбера, а хранилище отпускает его карту — открытые
трейсы, id родителя, исходящие вызовы, значения, собранные `add()`.

Теряется закрывающее обновление. Родительский трейс остаётся на бэкенде со статусом
`started`, а незавершённые исходящие вызовы не получают тега `__interrupted`: подметания
процессора видят только текущую единицу, и ни одна следующая до них не доберётся. При
`array` следующий запрос или джоба в том же процессе закрывали эти вызовы, как только им
было больше пяти минут, — родительский трейс и там оставался `started`, — и это
единственное, чем приходится заплатить.

Изнутри пакета это не чинится. Уборка во время уничтожения файбера не имеет права делать
ввод-вывод: `Fiber::suspend()` бросает `Cannot suspend in a force-closed fiber` из
`finally` внутри него и `Cannot suspend outside of a fiber` из деструктора после него, —
а отправка трейса под таким рантаймом это ровно точка приостановки.

**Гасите их на приёмнике**: трейс, от которого несколько минут нет обновлений,
закончился, что бы ни случилось с процессом, который его начал. Это единственное место,
которое смотрит на трейс после смерти процесса, и оно же покрывает фатальную ошибку и
убийство по памяти — то, чего не покроет ничто, исполняемое внутри процесса.

### Длительности в долгоживущем процессе

`LARAVEL_START` определяется один раз, во входном скрипте, там, где начинается *процесс*.
Под php-fpm процесс и есть этот запрос, измеряемая ею загрузка — его загрузка, и от неё
считаются и `boot_time`, и длительность. Под сервером, который загружается один раз и
дальше обслуживает часами — Octane, RoadRunner, воркерный режим FrankenPHP, корутинный
рантайм, — это старт воркера, и счёт от неё выдаёт аптайм воркера за длительность каждого
запроса: одно и то же число на каждом трейсе, растущее весь день.

Поэтому константа берётся только там, где она и есть начало этого запроса. Процесс,
поднятый из консоли и отвечающий на HTTP, — долгоживущий сервер, что бы он о себе ни
говорил, и не берёт её вовсе. Под любым другим SAPI её тратит первый трассируемый запрос
процесса и больше никакой. Все остальные меряют от момента, когда middleware этого пакета
увидела запрос, — он взят внутри хода выполнения самого запроса, то есть принадлежит
именно ему, — и пишут `boot_time` равным `-1`: загрузку, которой они не дожидались,
присваивать себе нечего.

И ни при каком рантайме — не от `Kernel::requestStartedAt()`: это одно поле на весь
процесс, и запрос, стартовавший рядом, перезапишет его более поздним временем, то есть
началом в будущем, то есть отрицательной длительностью.

Две вещи при этом остаются за бортом, обе небольшие и обе недостижимые изнутри пакета.
Там, где константа не берётся, не считается отрезок от входа в ядро до этой middleware —
глобальные middleware перед ней; рантайму, которому он нужен, придётся отдать момент
приёма запроса самому, потому что более ранней точки в воркере, поднятом часы назад, не
существует (`REQUEST_TIME_FLOAT` там тоже про старт процесса). И под воркером, чей SAPI не
консольный, первый запрос засчитает себе загрузку, которой не дожидался: один трейс на
воркер, и отличить эту загрузку от медленной нечем.

### Что покорутинно, а что нет

Покорутинно: id текущего родительского трейса, стек открытых родительских трейсов, флаг
паузы, карта detached-трейсов (исходящих вызовов), открытые родительским вотчером запросы
и команды, открытые вотчером HTTP-клиента исходящие вызовы, обрабатываемые джобы и
значения, собранные `add()`.

Процессное, и это осознанно: список включённых вотчеров, колбэки, зарегистрированные
через `add(fn() => ...)`, и буфер пачек диспатчера трейсов — покорутинный перестал бы
набирать пачки и умножил бы число джоб.

Эти колбэки общие — тем они и правила, а не значения, — поэтому регистрируйте их один
раз, из сервис-провайдера, и пусть они читают нужное в момент вызова:
`add('tenant', fn() => tenant()?->id())`. Замыкание, зарегистрированное на каждый запрос
и захватившее объекты этого запроса, будет вычисляться и для трейсов всех остальных
единиц — то есть положит данные одного запроса в трейсы другого, ровно то, о чём весь
этот раздел. Обычное значение принадлежит своей единице и безопасно где угодно.

Клиент сокета — ни то, ни другое: он держит небольшой пул соединений — то, с которым его
построили, плюс те, что открывает через `Connection::fresh()`, — и отправитель занимает
одно от первого записанного байта до последнего прочитанного. Процесс, отправляющий по
одной пачке за раз, открывает ровно одно и держит его, как и раньше; одновременные
отправители получают каждый своё, а не чередуют кадры в общем потоке, и до восьми
соединений остаются для переиспользования, остальные закрываются при возврате. Про
файберы там ничего не знают, поэтому это работает при любом способе делать что-то
одновременно.

Могут ли отправители вообще залезть в чужой обмен — свойство рантайма, а не этого пакета:
голый PHP-файбер приостанавливается только там, где сам сказал, а `Connection` не говорит
нигде. Рантайм, превращающий вызов над потоком в точку приостановки — ровно то, ради чего
корутины и заводят, — может. Там, где не может, пул ничего не стоит.

### Вотчер, которому конкурентность не идёт

**Вотчер дампов** подменяет обработчик `VarDumper` — глобальный для PHP — на время
одного `dump()`. `dump()` из другой единицы работы, попавший в это окно, не
трассируется. Не опасно, но это телеметрия, которой вы не увидите.

## Диспатчеры

### Диспатчер queue

Трейсы отправляет `SendTracesJob`, который ставится в очередь на
`SLOGGER_DISPATCHER_QUEUE_CONNECTION` и `SLOGGER_DISPATCHER_QUEUE_NAME`. Воркеры для неё
пакет не запускает: держите хотя бы один воркер на этом коннекшене и очереди так же, как
держите любую другую очередь, — Supervisor, systemd, Horizon:

```bash
php artisan queue:work slogger-rabbitmq --queue=slogger
```

Джоба несёт свои tries и backoff, и они важнее опций воркера, поэтому ни `--tries`, ни
`--backoff` воркеру не нужны. `queue:work` и `horizon:work` — воркер под Horizon — по
умолчанию исключены из вотчера команд, так что воркер сам себя не трассирует.

- Родительские и осиротевшие (orphan) трейсы ставятся в очередь немедленно, по джобе на
  каждый.
- Дочерние трейсы буферизуются и ставятся в очередь группами по 5; каждое обновление
  трейса — закрытие родителя — ставится в очередь сразу, вместе со всем, что лежит в
  буфере.
- То, что ещё в буфере, ставится в очередь при завершении процесса.
- Сбой постановки в очередь никогда не доходит до приложения: батч дропается, а
  предупреждение (`dropped N trace dispatches`, не чаще раза в минуту) уходит в
  лог-канал SLogger.

### Диспатчер memory

Держит каждый трейс в процессе, незамаскированным и неотправленным, до `flush()`;
`findCreating()`, `findUpdating()` и `totalCount()` есть для проверок в тестах.
Предназначен для тестов и локальной разработки, а не для долгоживущих процессов.

## Тестирование

Тесты запускаются в Docker через makefile:

```bash
make setup                # once: build, start, composer install
make test                 # phpunit
make check                # cs-fixer + phpstan + phpunit
make check-laravel-all    # `check` on Laravel 10, 11 and 12
```

`vendor/bin/phpunit` тоже работает, если зависимости установлены локально. `phpunit.xml`
включает SLogger с диспатчером `memory`, `BaseTestCase` ставит in-memory sqlite и
`sync`-коннекшен очереди, а testbench загружает `workbench/config/slogger.php`.

## Диагностика проблем

- Нет трейсов: проверьте `SLOGGER_ENABLED=true`, что вотчер включён, а middleware
  применён к роутам, и поищите в лог-канале SLogger `dropped N trace dispatches` —
  например, при незаданном `SLOGGER_DISPATCHER_QUEUE_CONNECTION`.
- Диспатчер queue не отправляет: воркер должен слушать этот коннекшен *и* очередь
  (`--queue=slogger`). Ошибки отправки никогда не доходят до репортинга ошибок
  приложения: ищите в лог-канале SLogger `dropped N traces`, `auth failed` (токен) или
  ошибки сокета (`SLOGGER_DISPATCHER_QUEUE_SOCKET_CLIENT_URL`, запущен ли приёмник).

## Обновление

### С 2.1

- **`slogger:dispatcher:start` и `slogger:dispatcher:stop` удалены.** Пакет больше не
  запускает собственные воркеры очереди: запускайте их так же, как любую другую очередь, —
  Supervisor, systemd, Horizon, см. [Диспатчер queue](#диспатчер-queue). Остановите старый
  диспатчер перед обновлением и уберите его из менеджера процессов.
  `SLOGGER_DISPATCHER_QUEUE_WORKERS_COUNT` больше не читается, а `storage/slogger/`, где
  лежало только состояние диспетчера, можно удалить. `horizon:work` добавлен в список
  `excepted` вотчера команд по умолчанию; в опубликованный конфиг он сам не попадёт —
  добавьте его вручную, если используете Horizon.
- **Профилирование удалено** вместе с `SLOGGER_PROFILING_ENABLED` и секцией `profiling`
  конфига. Оставшаяся в опубликованном конфиге секция игнорируется.
- `ext-pcntl`, `ext-posix` и `symfony/process` пакету больше не нужны.
- Изменения API, если вы расширяете ядро: удалены `TraceDispatcherInterface::getProcessor()`,
  `DispatcherProcessorInterface`, `QueueDispatcherProcessor`,
  `DispatcherQueueConfig::getWorkersNum()`, `WatchersConfig::profilingEnabled()` и
  `LocalStorage`, `TraceUpdateObject` лишился аргумента `profiling`, а `QueueDispatcher`
  больше не принимает приложение.

### До 2.1

Поведение по умолчанию не меняется, публичные методы — тоже. Изменились два
конструктора, и это важно, только если вы строите их сами или переопределяете в
наследнике:

| Класс | Что изменилось |
| --- | --- |
| `TraceIdContainer` | теперь принимает `TraceContextInterface`; раньше конструктора не было |
| `HttpMiddleware` | теперь принимает `TraceIdContainer` вторым аргументом |

У `Connection` появился `fresh()`, а `SocketClient` и `ApiClientFactory` сохранили свои
аргументы.

`Processor`, `RequestWatcher`, `CommandWatcher`, `JobWatcher`, `HttpClientWatcher` и
`TraceDataComplementer` принимают `TraceContextInterface` **последним** аргументом. Все
они резолвятся из контейнера, поэтому больше менять ничего не нужно.

### До 2.0

Маскирование переехало из отслеживаемого приложения в джобу диспетчера.

- **Маскирования на уровне вотчеров больше нет.** `input.headers_masking`,
  `input.parameters_masking`, `output.headers_masking`, `output.fields_masking` и `masks`
  у вотчера моделей больше не читаются. Остатки в опубликованном конфиге просто
  игнорируются, ошибки не будет — а значит, всё, что вы туда дописали, маскироваться
  перестанет. **Сверьте свои ключи с `masking.full_keys`** и перенесите то, чего в
  поставляемом списке нет: он покрывает прежние дефолты плюс `ssn`, `iban` и
  `card_number`, но не то, что вы добавляли сами.
- **Ключи — это маски, а не подстроки.** Маска сверяется с ключом целиком и с каждым
  его словом по отдельности: `auth` ловит `php-auth-pw` и `x-auth-user`, но не
  `author`, а `*token*` ловит `api_token` и `tokenizer`. Если вы переносите ключи из
  прежних списков у вотчеров — там это тоже были паттерны `Str::is` (`*token*`,
  `*password*`), так что они переезжают как есть.
- **Вместо них глобальные списки** — `masking.full_keys`, `masking.partial_keys` и
  `masking.value_patterns`, последний сверяется со значением, а не с ключом. Читаются
  они из вашего конфига, поэтому **переиздайте конфиг** (или добавьте секцию `masking`
  руками): в опубликованном до 2.0 конфиге этой секции нет вовсе, а отсутствующий
  список ничего не маскирует.
- **От замаскированного секрета не остаётся ничего.** Значение под ключом из
  `masking.full_keys` превращается в `********` — прошлый релиз оставлял открытыми первую и
  последнюю треть строки, а для токена или пароля это не маска. Значения под ключами из
  `masking.partial_keys` (адреса, телефоны, имена) сохраняют по два символа с каждого
  края — ровно столько, чтобы различать записи.
- **Перезапускайте воркеры slogger вместе с приложением.** Маскирует теперь воркер, и
  воркер на старом 1.x разберёт очередь версии 2.0 и отправит батчи незамаскированными.
  Выкатывайте воркеры первыми или дайте очереди slogger опустеть на переключении.
- **В очереди slogger теперь лежат незамаскированные данные трейсов.** Маскирование
  происходит на выходе, поэтому всё, что собрали вотчеры, лежит в хранилище очереди до
  момента отправки. Дайте этой очереди те же правила хранения и доступа, что и самим
  данным: отдельное подключение или отдельная база Redis и никаких долгоживущих записей
  в `failed_jobs`.
- **Структура данных трейса изменилась** там, где старая форма прятала данные приложения
  от маскера или уводила их в тег, который ничем не маскируется:
  - значения кеша лежат под своим кеш-ключом (`cache.<key>.value`);
  - почтовые адреса — под `message` парами `email`/`full_name` вместо «адрес в роли
    ключа»;
  - маршруты анонимного notifiable переехали из строки `Anonymous:...` в
    `recipients` (а адрес, оставшийся в такой строке, теперь всё равно
    маскируется паттерном значения);
  - query-строка url отделена в `query` и `query_string`;
  - **значения параметров маршрута больше не теги и больше не `uri`.** Запрос
    помечается и называется шаблоном маршрута — `/reset/{token}`, — а значения лежат в
    `route_parameters`, где список ключей достаёт их по имени параметра;
  - у исходящего `uri` вырезается userinfo, поэтому учётки, записанные в url, не
    попадают в тег;
  - значения, добавленные через `TraceDataComplementer::add()`, лежат под
    `__add`, а не на верхнем уровне, — именно это делает их досягаемыми для
    маскера. Обычное значение принадлежит текущей единице работы и стирается,
    когда она закончилась: следующий джоб в воркере `queue:work` и следующий
    запрос под Octane его не унаследуют. `Closure` — вторая половина истории:
    регистрируется один раз, на процесс, и вычисляется заново для каждого трейса —
    ровно то, что нужно для `fn() => auth()->id()` в сервис-провайдере.
- **XML-тело теперь записывается**, под ключом `__xml`, — раньше оно терялось: оба
  вотчера гоняли любое тело через `json_decode`, а XML давал `[]`. Потребитель,
  считавший, что тело — всегда разобранная структура, теперь увидит и массив из одного
  ключа с документом-строкой.
- **У исходящего заголовка родительского трейса поменялось значение.** Раньше он нёс
  трейс, окружающий вызов; теперь — трейс самого вызова, поэтому вызываемый сервис
  вешает свой трейс под этот вызов, а не рядом с ним. В межсервисном дереве
  добавляется уровень. Перенастраивать ничего не нужно, но приёмник, который считает
  глубину, разницу увидит.

  Всё, что читает эти поля на приёмной стороне, нужно обновить.
- **Laravel 10.26** — новый минимум. Коду в `src/` нужен 10.12 (там появился
  `JobTimedOut`), но тесты работают через workbench у testbench, а его самый ранний
  релиз требует 10.26 — непроверяемый минимум минимумом не считается. Заявленный до
  этого 10.17 не был правдой ни минуты: окружение там ставится, но 152 теста падают —
  testbench, который идёт в паре с 10.17, не умеет искать конфиг workbench, и пакет
  считает себя выключенным.
- Изменения API, если вы сами собираете форматтеры: у `RequestDataFormatter` пропали
  аргументы `requestHeaders`, `requestParameters`, `responseHeaders`, `responseFields`
  и парные методы `add*()`, а `MaskHelper::maskArrayByList()` и `maskArrayByPatterns()`
  удалены. `MaskHelper::maskValue()` теперь маскирует строку целиком, а частично
  маскирует `maskValuePartially()`.
- Изменения API, если вы расширяете ядро: `Processor::stopDetached()` удалён — `stop()`
  закрывает родительский трейс, как бы тот ни был начат, — вместе с
  `Processor::handleSeparateTracing()` и `Processor::registerWatcher()`, который теперь
  делает сам сервис-провайдер. У `DispatcherProcessorInterface` появился
  `getChildCommandName()`: мастер сохраняет это имя и по нему ищет своих детей, поэтому
  оно должно совпадать с тем, что покажет таблица процессов.
