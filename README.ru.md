# SLogger Laravel

[English](README.md) | **Русский**

SLogger Laravel — пакет трейсинга/наблюдаемости (observability) для Laravel-приложений. Он записывает трейсы запросов/команд/джобов/событий и т.д. и доставляет их на удалённый бэкенд через настраиваемые диспатчеры.

Этот README описывает установку, конфигурацию, вотчеры, маскирование, диспатчеры, профилирование и сценарии использования.

## Обновление до 1.3

Маскирование переехало из отслеживаемого приложения в джобу диспетчера.

- **Маскирования на уровне вотчеров больше нет.** `input.headers_masking`,
  `input.parameters_masking`, `output.headers_masking`, `output.fields_masking` и `masks`
  у вотчера моделей больше не читаются. Остатки в опубликованном конфиге просто
  игнорируются, ошибки не будет — а значит, всё, что вы туда дописали, маскироваться
  перестанет. **Перенесите свои ключи в `masking.full_keys`**: дефолты покрывают
  дефолты, но не `ssn`, `iban`, `card` и прочее, что вы добавляли сами.
- **Вместо них глобальные списки** — `masking.full_keys`, `masking.partial_keys` и
  `masking.value_patterns`, последний сверяется со значением, а не с ключом.
  Опубликованный конфиг теперь мержится с пакетным, поэтому дефолты работают и без
  переиздания конфига; добавляйте секцию к себе, только если хотите её изменить.
  Отсутствующий список берётся из конфиг-файла самого пакета, поэтому устаревший кеш
  конфига не оставит вас совсем без маскирования.
- **От замаскированного секрета не остаётся ничего.** Значение под ключом из
  `masking.full_keys` превращается в `********` — прошлый релиз оставлял открытыми первую и
  последнюю треть строки, а для токена или пароля это не маска. Значения под ключами из
  `masking.partial_keys` (адреса, телефоны, имена) сохраняют по два символа с каждого
  края — ровно столько, чтобы различать записи.
- **Перезапускайте воркеры slogger вместе с приложением.** Маскирует теперь воркер, и
  воркер на старом 1.2.x разберёт очередь версии 1.3 и отправит батчи незамаскированными.
  Выкатывайте воркеры первыми или дайте очереди slogger опустеть на переключении.
- **В очереди slogger теперь лежат незамаскированные данные трейсов.** Маскирование
  происходит на выходе, поэтому всё, что собрали вотчеры, лежит в хранилище очереди до
  момента отправки. Дайте этой очереди те же правила хранения и доступа, что и самим
  данным: отдельное подключение или отдельная база Redis и никаких долгоживущих записей
  в `failed_jobs`.
- **Структура данных трейса изменилась** там, где старая форма прятала данные приложения
  от маскера или уводила их в тег, который ничем не маскируется:
  - значения кеша лежат под своим кеш-ключом (`cache.<key>.value`);
  - почтовые адреса — под `message` парами `email`/`full_name` вместо «адрес в роли
    ключа»;
  - маршруты анонимного notifiable переехали из строки `Anonymous:...` в
    `target.recipients` (а адрес, оставшийся в такой строке, теперь всё равно
    маскируется паттерном значения);
  - query-строка url отделена в `query` и `query_string`;
  - **значения параметров маршрута больше не теги и больше не `uri`.** Запрос
    помечается и называется шаблоном маршрута — `/reset/{token}`, — а значения лежат в
    `route_parameters`, где список ключей достаёт их по имени параметра;
  - у исходящего `uri` вырезается userinfo, поэтому учётки, записанные в url, не
    попадают в тег;
  - значения, добавленные через `TraceDataComplementer::add()`, лежат под
    `__additional`, а не на верхнем уровне, — именно это делает их досягаемыми для
    маскера.
- **XML-тело теперь записывается**, под ключом `__xml`, — раньше оно терялось: оба
  вотчера гоняли любое тело через `json_decode`, а XML давал `[]`. Потребитель,
  считавший, что тело — всегда разобранная структура, теперь увидит и массив из одного
  ключа с документом-строкой.
- **У исходящего заголовка родительского трейса поменялось значение.** Раньше он нёс
  трейс, окружающий вызов; теперь — трейс самого вызова, поэтому вызываемый сервис
  вешает свой трейс под этот вызов, а не рядом с ним. В межсервисном дереве
  добавляется уровень. Перенастраивать ничего не нужно, но приёмник, который считает
  глубину, разницу увидит.

  Всё, что читает эти поля на приёмной стороне, нужно обновить.
- **Laravel 10.17** — новый минимум. Коду в `src/` нужен 10.12 (там появился
  `JobTimedOut`), но 10.17 — самый старый релиз, на который вообще ставится тестовое
  окружение, а непроверяемый минимум минимумом не считается.
- Изменения API, если вы сами собираете форматтеры: у `RequestDataFormatter` пропали
  аргументы `requestHeaders`, `requestParameters`, `responseHeaders`, `responseFields`
  и парные методы `add*()`, а `MaskHelper::maskArrayByList()` и `maskArrayByPatterns()`
  удалены. `MaskHelper::maskValue()` теперь маскирует строку целиком, а частично
  маскирует `maskValuePartially()`.

## Требования

- PHP >= 8.2
- Laravel 10.17+ (протестировано на 10, 11 и 12)
- Драйвер очередей для диспатчера `queue`
- Опционально: расширение XHProf для профилирования

## Установка

1) Установите пакет (через Composer в вашем приложении):

```bash
composer require slogger/laravel
```

2) Опубликуйте конфиг:

```bash
php artisan vendor:publish --tag=slogger-laravel
```

3) Настройте env и `config/slogger.php` (см. ниже).

## Быстрый старт

Включите и используйте диспатчер `queue`:

```dotenv
SLOGGER_ENABLED=true
SLOGGER_TOKEN=your-api-token
SLOGGER_DISPATCHER=queue
SLOGGER_DISPATCHER_QUEUE_CONNECTION=redis
SLOGGER_DISPATCHER_QUEUE_NAME=slogger
SLOGGER_LOG_REQUESTS_ENABLED=true
```

Затем запустите воркеры диспатчера:

```bash
php artisan slogger:dispatcher:start
```

## Бэкенд сбора трейсов

SLogger Laravel отправляет трейсы в отдельный бэкенд-сервис. Референсный проект бэкенда:

```text
https://github.com/sprust/slogger
```

Используйте его инструкции по установке, чтобы развернуть сервер и настроить URL/токен API-клиента в этом пакете.

### Свой бэкенд / клиент

Бэкенд можно заменить, предоставив собственный API-клиент. Переопределите `ApiClientFactory::create` и верните свою реализацию `SLoggerLaravel\\Dispatcher\\ApiClients\\ApiClientInterface`, отправляющую трейсы на ваш бэкенд.

## Конфигурация

Вся конфигурация находится в `config/slogger.php` с переопределением через env. Ключевые секции:

### Общее

```dotenv
SLOGGER_ENABLED=false
SLOGGER_TOKEN=
SLOGGER_TRACE_ID_PREFIX=
SLOGGER_LOG_CHANNEL=daily
```

- `SLOGGER_ENABLED`: глобальное включение/выключение всего трейсинга.
- `SLOGGER_TOKEN`: API-токен для диспатчеров.
- `SLOGGER_TRACE_ID_PREFIX`: свой префикс для trace ID. Если пустой — используется slug от `app.name` или `app`.
- `SLOGGER_LOG_CHANNEL`: канал для внутренних ошибок пакета.

### Диспатчеры

```dotenv
SLOGGER_DISPATCHER=queue
SLOGGER_DISPATCHER_QUEUE_CONNECTION=slogger-rabbitmq
SLOGGER_DISPATCHER_QUEUE_NAME=slogger
SLOGGER_DISPATCHER_QUEUE_WORKERS_COUNT=3
SLOGGER_DISPATCHER_QUEUE_API_CLIENT=socket
SLOGGER_DISPATCHER_QUEUE_SOCKET_CLIENT_URL=tcp://0.0.0.0:0002
SLOGGER_DISPATCHER_QUEUE_SOCKET_CLIENT_TIMEOUT=10
```

- `SLOGGER_DISPATCHER`: `queue` или `memory`.
- Диспатчер `queue` запускает воркер-процессы (по аналогии с Horizon) и отправляет трейсы через HTTP- или socket-клиент.
- Диспатчер `memory` хранит трейсы в памяти (удобно для тестов/разработки).

`SLOGGER_DISPATCHER_QUEUE_CONNECTION` **обязателен** для диспатчера `queue` — фолбэка на
`QUEUE_CONNECTION` нет намеренно: телеметрия не должна молча делить queue-коннекшен с
приложением. Используйте выделенный коннекшен.

`SLOGGER_DISPATCHER_QUEUE_SOCKET_CLIENT_TIMEOUT` — таймаут чтения/записи socket-клиента в
секундах (по умолчанию `10`). Он даёт запас, когда приёмник перегружен и подтверждение реально
задерживается; таймаут установки соединения — отдельный и остаётся 2 секунды.

Если приёмник закрыл соединение (рестарт, деплой, сетевой сбой), клиент это замечает и
переподключается прозрачно — ровно одна повторная попытка на батч. Таймауты так **не**
ретраятся: это превратило бы перегруженный приёмник в шторм переподключений — их обрабатывает
политика ретраев джобы ниже.

Ретраи отправки зафиксированы намеренно: 5 попыток с паузами 5/10/30/60 секунд между ними.
После исчерпания попыток батч **дропается** с rate-limited предупреждением в лог-канале
SLogger — телеметрия никогда не засоряет хранилище `failed_jobs`.

### Профилирование

```dotenv
SLOGGER_PROFILING_ENABLED=true
```

Включает XHProf-профилирование для трейсов HTTP-клиента (см. раздел «Профилирование»).

### Заголовок родительского трейса запроса

```dotenv
SLOGGER_REQUESTS_HEADER_PARENT_TRACE_ID_KEY=x-parent-trace-id
```

Позволяет связывать дочерние трейсы с родительскими запросами через кастомный заголовок.
Middleware читает его из входящего запроса и ставит на возвращаемый ответ, так что
клиент его действительно получает. (Раньше заголовок ставился в `terminate()`, который
под FPM выполняется уже после отправки ответа, — межсервисная корреляция работала
только в тестах.)

### Вотчеры (включение/выключение)

```dotenv
SLOGGER_LOG_COMMANDS_ENABLED=true
SLOGGER_LOG_JOBS_ENABLED=true
SLOGGER_LOG_REQUESTS_ENABLED=true
SLOGGER_LOG_CACHE_ENABLED=true
SLOGGER_LOG_DATABASE_ENABLED=true
SLOGGER_LOG_DUMP_ENABLED=true
SLOGGER_LOG_EVENT_ENABLED=true
SLOGGER_LOG_GATE_ENABLED=true
SLOGGER_LOG_HTTP_ENABLED=true
SLOGGER_LOG_LOG_ENABLED=true
SLOGGER_LOG_MAIL_ENABLED=true
SLOGGER_LOG_MODEL_ENABLED=true
SLOGGER_LOG_NOTIFICATION_ENABLED=true
SLOGGER_LOG_SCHEDULE_ENABLED=true
```

## Что записывает SLogger

Каждый трейс содержит:
- `trace_id`, `parent_trace_id`, `type`, `status`, `tags`
- `data` (данные конкретного вотчера)
- `duration`, `memory`, `cpu`, `logged_at`

`memory` — это процент использования `memory_limit`, и он **null, когда лимита нет**
(`memory_limit = -1`, дефолт CLI): процентом быть не от чего. `cpu` — минутный load
average в процентах от мощности машины, нормированный на число ядер; на перегруженной
машине может быть больше 100.

Основные данные вотчеров:
- `request`: url (без query-строки), метод, action, query/query_string, route_parameters, заголовки/параметры, ответ (для JSON- и XML-ответов)
- `job`: коннекшен, payload, статус (`processed`, `failed`, `released_after_exception`, `timed_out`, `exception_occurred`), исключение
- `event`: слушатели, broadcast, опционально сериализованный payload
- `model`: действие, класс модели, ключ, изменения
- `mail`: mailable/notification, queued, `message` (from/reply_to/to/cc/bcc парами `email`/`full_name`, тема)
- `notification`: notifiable, канал, queued, `target.recipients`, ответ
- `cache`: тип, ключ и `cache.<key>` (значение, теги, время жизни)
- `db`: запрос, биндинги (маскируются, если маскирование не выключено целиком), время
- `http-client`: метод, url, query/query_string, запрос/ответ (параллельные запросы трейсятся независимо, так что `Http::pool()` работает)
- `schedule`: команда, описание, cron, вывод
- `dump`, `log`, `gate`: информация о dump/сообщении/ability

Воркер очереди завершает job по таймауту из обработчика `SIGALRM`, то есть посреди работы
job, и сразу после этого убивает себя. Трейсы, открытые внутри job и ещё не закрытые к
этому моменту, закрываются со статусом `failed` и тегом `__interrupted`, сохраняя уже
собранные данные; job, отправленный на повтор вместо `failed`, закрывается по событию
`JobTimedOut`. Трейс всё ещё может остаться в статусе `started`, если сигнал придёт во
время отправки трейса в диспетчер — там трейсинг приостановлен, и события таймаута
теряются, — или если воркер убит сигналом, который он не обрабатывает.

## Запросы

### Middleware

Для трейсинга HTTP-запросов добавьте middleware к нужным роутам:

```php
\SLoggerLaravel\Middleware\HttpMiddleware::class
```

### Конфиг вотчера запросов

`config/slogger.php`:

```php
'watchers' => [
    [
        'class'   => \SLoggerLaravel\Watchers\Parents\RequestWatcher::class,
        'enabled' => env('SLOGGER_LOG_REQUESTS_ENABLED', false),
        'config'  => [
            // логировать только совпавшие пути (опционально)
            'only_paths' => [
                // 'api/*',
            ],

            // пропускать совпавшие пути
            'excepted_paths' => [
                // 'health',
            ],

            'input' => [
                // применять форматирование входных данных только для этих путей
                'only_paths' => [
                    // 'api/*',
                ],

                // скрывать все параметры запроса для этих путей
                'hidden_paths' => [
                    // 'auth/*',
                ],

            ],

            'output' => [
                // применять форматирование ответа только для этих путей
                'only_paths' => [
                    // 'api/*',
                ],

                // скрывать все данные ответа для этих путей
                'hidden_paths' => [
                    // 'auth/*',
                ],

                // лимит размера json-ответа (в байтах)
                'max_content_length' => 1048576,
            ],
        ],
    ],
],
```

#### `only_paths`
- `only_paths` (верхний уровень): логировать только совпавшие пути запросов.
- `input.only_paths`: применять форматирование входных данных только к совпавшим путям (остальные вычищаются).
- `output.only_paths`: применять форматирование ответа только к совпавшим путям (остальные вычищаются).

Паттерны сопоставляются через Laravel `Str::is`.

### Размер JSON-ответа

Тело, которое не JSON, но **разбирается как XML** — SOAP-конверт, XML-API, — кладётся
как сам документ, под ключом `__xml`:

```json
{"__xml": "<order><api_token>********</api_token></order>"}
```

А не как массив, полученный из него: так теряются атрибуты, повторяющиеся элементы и
неймспейсы, а трейс, который больше не совпадает с описываемым документом, стоит немного.
Маскер умеет заглядывать внутрь такой строки (см. «Правила маскирования»), поэтому
документ маскируется на месте. Работает в обе стороны и у обоих вотчеров: входящее тело
запроса, которое Laravel не разбирает в `input()`, исходящее тело и оба ответа.

**Отправитель должен сам это сказать.** Тело записывается как XML, только если его
`Content-Type` — XML-ный (`application/xml`, `text/xml`, `application/soap+xml`, `*+xml`)
**и** оно разбирается как XML. Одного разбора мало: HTML-фрагмент — то, чем отвечает
htmx- или Turbo-эндпоинт, — это валидная разметка с CSRF-токеном в `value="…"`, а маскер
сверяет *имена* и до него не дотянется. Тело, которое ни JSON, ни помеченное как XML,
отбрасывается, как и раньше.

Тело также отбрасывается — с `{"__skipped": "body_too_large"}` — если оно больше того,
что маскер станет читать (1 МБ), и с `{"__skipped": "non_utf8_body"}`, если это не
валидный UTF-8: данные трейса сериализуются через `json_encode`, и битые байты заменили
бы весь пейлоад этого трейса ошибкой кодировки, а не только тело.

Слишком большие ответы пропускаются и помечаются так:

```json
{"__skipped": "response_too_large"}
```

## Правила маскирования

Маскирование выполняется **в джобе диспетчера**, прямо перед отправкой батча, и никогда
не выполняется в отслеживаемом приложении. Приложение платит только за сбор данных и
передачу их дальше; обход пейлоада ключ за ключом оплачивают воркеры диспетчера. Отсюда
два следствия:

- **В очереди лежат незамаскированные данные трейсов.** Всё, что собрали вотчеры, лежит
  в хранилище очереди до момента отправки, поэтому очередь slogger настолько же
  чувствительна, как и сами трейсы: выделите ей своё подключение, держите короткое
  время хранения и не давайте упавшим батчам копиться в `failed_jobs`.
- Диспетчер `memory` не маскирует — у него нет джобы. Это средство для разработки и
  тестов, никуда наружу он ничего не отправляет.

Вотчеры не маскируют. В рантайме они только скрывают и урезают: `only_paths`,
`excepted_paths`, `hidden_paths`, `max_content_length`, списки `excepted` у вотчеров.
Единственное исключение — вотчер базы: биндинги позиционные, никакой список ключей до
них не дотянется, поэтому он маскирует их там же, где записывает. Все подряд, независимо
от типа и длины: по биндингу не понять, пароль это или номер страницы, а PIN, OTP и номер
счёта — все короткие и числовые.

### Списки ключей

```php
'masking' => [
    // значение под подходящим ключом заменяется целиком — от него не остаётся ничего
    'full_keys' => [
        'token', 'pass', 'auth', 'secret', 'private', 'apikey',
        'api_key', 'api-key', 'credential', 'sign', 'cookie',
    ],

    // значение под подходящим ключом сохраняет по два символа с каждого края
    'partial_keys' => [
        'email', 'phone', 'recipient', '_name',
        'lastname', 'firstname', 'surname',
    ],

    // сверяются со значением, а не с ключом, и маскируются по месту
    'value_patterns' => [
        'email' => '/[\w.+-]+@[\w-]+\.[\w.-]*[\w-]/u',
    ],
],
```

Оба списка — подстроки ключа без учёта регистра; маскирование выключено, только когда
пусты все три списка, включая `value_patterns`. Этот же выключатель управляет биндингами
вотчера БД — единственным, что ещё маскируется в самом приложении. Ключ подходит, если
*содержит* одну из подстрок, — подходят и `customer_email`, и `API_KEY`, и `lastName`.
Совпадение на родительском ключе распространяется на всё поддерево: `context.auth`
покрывает и `context.auth.method` — родитель при этом должен быть уровнем ниже верхнего,
потому что верхний уровень не сверяется вовсе (см. ниже). Ключ, попавший в оба списка,
маскируется целиком — строгий список побеждает.

Разделение — это и есть суть. Секрет обесценивается от любой утечки, поэтому
`masking.full_keys` заменяет значение полностью: `********`, фиксированной ширины, чтобы не
утекла ещё и длина секрета. Адрес, телефон или имя нужны в основном чтобы различать
записи, поэтому `masking.partial_keys` сохраняет по два символа с каждого края:
`john.doe@example.com` превращается в `jo****************om`. **Никогда не кладите
секрет в `partial_keys`**: оставшегося хватит, чтобы связывать записи между собой, а для
короткого значения — чтобы его угадать.

Значение, которое является **строкой с документом**, разбирается, маскируется и
запаковывается обратно: приложения передают целые документы строками — каст `array` у
Eloquent кладёт такой прямо в изменения модели, SOAP-вызов приезжает целиком, — а ключ,
под которым лежит эта строка, ничего не говорит о её содержимом. Разбираются два
формата:

- **JSON** — строки, начинающиеся с `{` или `[`. При переупаковке нормализуется
  экранирование, а число, слишком большое или слишком точное для float в PHP, теряет
  точность.
- **XML** — строки, которые разбираются как XML. Имена элементов и атрибутов сверяются
  так же, как ключи объекта, совпадение покрывает поддерево (`<auth>` маскирует всё
  внутри), namespace-префикс имя не прячет (`soap:Envelope` сверяется по `Envelope`),
  CDATA маскируется на месте, а к комментариям и processing-инструкциям применяются
  паттерны значений. При пересборке может нормализоваться незначимый пробельный
  материал и кавычки атрибутов; документ, у которого не было XML-декларации, её не
  получит.
- **Родная сериализация PHP** — строки, начинающиеся с `a:<n>:{`. Сессия, лежащая в
  кеше, — как раз такая: в ней CSRF-токен и хеш пароля под ключами, которые списки
  ловят. Объекты при чтении никогда не создаются.

Документ, в котором **ничего** не совпало, остаётся байт в байт.

XML-сущности не разворачиваются никогда, поэтому документ, приехавший снаружи, не
заставит диспетчер прочитать локальный файл или развернуть billion-laughs-бомбу во время
маскирования — маскирование идёт в воркере над пейлоадами, которые писало не приложение.
Отсюда два следствия, и оба падают в **закрытую** сторону: документ, значения которого
живут во внутреннем DTD, маскируется целиком, потому что маска вокруг `&secret;` при
живом объявлении читается как защита, ею не являясь; и документ с объявлениями, который
вообще не разобрался, маскируется целиком по той же причине.

Всё остальное, что просто начинается с `<` — кусок текста, страница, — не трогается, к
нему применяются только паттерны значений, как к обычному тексту.

Значение под ключом **`query_string`** маскируется параметр за параметром, а не целиком:
из `page=2&api_token=secret` останется страница и пропадёт токен. Именно туда вотчеры
запросов кладут query-строку url: url — это ещё и тег, и заголовок, а их ничто не
маскирует.

### Паттерны значений

Некоторые вещи опознаются по собственной форме, где бы они ни оказались, и ни один ключ
на них не указывает: адрес внутри `Anonymous:mail,john@example.com` или посреди
лог-сообщения. `masking.value_patterns` — это регулярки, которые сверяются со
**значением**, а найденное маскируется по месту, частично, так что остальная строка
остаётся читаемой:

```
'invoice sent to john.doe@example.com'  ->  'invoice sent to jo****************om'
```

Они не привязаны к ключу, поэтому, в отличие от списков ключей, работают и на первом
уровне, достают внутрь JSON-строк и query-строк, в **ключи массивов** и в **теги**
трейса — а теги больше не маскирует ничто. Совпадение
по ключу всё равно главнее: у `token` с адресом внутри не останется ничего, а не только
середина. Некорректная регулярка просто отбрасывается, а не сыплет warning'ами на каждой
строке каждого трейса.

Списки ключей и паттерны закрывают разное и рассчитаны на совместную работу: `recipient`
в `partial_keys` ловит телефон под `target.recipients.vonage`, который никакой адресный
паттерн не увидит.

**Первый уровень `data` трейса не маскируется никогда.** Этот уровень принадлежит
вотчеру, а не приложению: `connection_name`, `request`, `changes`, `context`, `bindings`
и прочее — фиксированная структура, а отслеживаемые данные начинаются уровнем ниже.
Поэтому сверка начинается внутри неё: `context.customer_email` и
`job.data.customer_email` маскируются, а `connection_name` остаётся читаемым, хотя и
содержит `_name`. Вотчеры, у которых на первом уровне лежали данные приложения, были
переделаны, чтобы правило работало и для них: значение кеша лежит под своим кеш-ключом
(`cache.<key>.value` — и тогда список сверяется именно с ключом), а почтовые адреса — под
`message` парами `email`/`full_name`.

Списки намеренно грубые: они замаскируют `sign` внутри `assignee` и `auth` внутри
`author`. Для телеметрии перестраховка безопаснее недосмотра; если нужное поле попало под
маску — уберите подстроку из списка.

### Куда список ключей не дотягивается

Некоторые поля — свободный текст, и никакое имя ключа не описывает, что внутри. Списки
ключей на них не действуют; работают только `value_patterns`, и только для того, у чего
есть узнаваемая форма:

| Поле | Что внутри |
| --- | --- |
| `log.message` | то, что залогировали |
| `dump.dump` | то, что дампнули, — `dd($user->api_token)` это ровно оно |
| `schedule.output` | stdout запланированной команды |
| `db.sql` и sql-фрагмент в тегах трейса `db` | сам запрос, хотя значения едут биндингами, а они маскируются |

Здесь средства — вотчерские: выключить вотчер или не класть секреты в то, что логируете
и дампите. **Теги** трейса в том же положении — голые строки, которые никакой ключ не
называет, — поэтому паттерны значений применяются и к ним.

### Замаскированные значения

Замаскированные значения сохраняют базовые типы, поэтому замаскированный пейлоад
остаётся той же формы, что и исходный:
- `null` -> `null`
- `bool` -> `false`
- `int` -> `0`
- `float` -> `0.0`
- `string` -> `********`, либо по два символа с каждого края при частичной маске
- объект -> `********` (объект с `__toString()` маскируется как своя строка)

Пустая строка остаётся как есть: маска на её месте утверждала бы, что там что-то было.

**Массив обходится, а не заменяется.** Подошедший ключ покрывает поддерево, поэтому
маскируется каждый *лист* под ним, а структура и имена ключей остаются:
`{"token":{"a":"secret","b":2}}` превращается в `{"token":{"a":"********","b":0}}`. Ключи
— тоже данные, когда их выбирает приложение (кеш-ключ сплошь и рядом выглядит как
`otp:<адрес>`), поэтому `value_patterns` применяются и к ключам массивов, и к тегам —
двум местам, куда список ключей не дотягивается.

## Трейсинг Guzzle / HTTP-клиента

Хендлер SLogger можно подключить к Guzzle:

```php
new \GuzzleHttp\Client([
    'base_uri' => 'https://url.com',
    'handler'  => app(\SLoggerLaravel\Guzzle\GuzzleHandlerFactory::class)->prepareHandler(
        (new \SLoggerLaravel\RequestPreparer\RequestDataFormatters())
            ->add(
                new \SLoggerLaravel\RequestPreparer\RequestDataFormatter(
                    urlPatterns: ['/api/auth/*', '*sensitive/some/*'],
                    hideAllRequestParameters: true,
                    hideAllResponseData: true
                )
            )
    ),
])
```

Форматтеры скрывают и урезают; чувствительные значения маскируются позже, в
джобе диспетчера.

## Диспатчеры

### Диспатчер queue

Запуск диспатчера (порождает воркеры очереди):

```bash
php artisan slogger:dispatcher:start
```

- Родительские трейсы отправляются немедленно.
- Дочерние трейсы батчатся (размер батча по умолчанию: 5).
- Осиротевшие (orphan) трейсы отправляются немедленно.
- При завершении процесса оставшиеся трейсы флашатся.

Остановка диспатчера:

```bash
php artisan slogger:dispatcher:stop
```

### Диспатчер memory

Хранит трейсы только в памяти. Предназначен для тестов/локальной разработки.

## Хранилище

SLogger не сохраняет трейсы локально. Единственный локальный файл — файл состояния диспатчера:

```text
storage/slogger/dispatcher-state-*.json
```

Папку имеет смысл добавить в ignore:

```gitignore
storage/slogger/*
```

## Конкурентные рантаймы (корутины)

Рантайм, исполняющий каждый запрос или джобу в своём `Fiber` и переключающийся между
ними на каждом async-вызове, ломает пакет, который держит per-request состояние в
процессных объектах. Всё, что slogger держит на единицу работы — стек трейсов, точка,
к которой цепляются дочерние трейсы, флаг паузы, открытые записи родительских вотчеров,
— оказалось бы общим для корутин, работающих вперемешку в одном процессе. Ломается это
тихо: не падение, а трейс, закрытый чужой корутиной, и дети, повисшие под чужим
родителем.

Всё это состояние живёт в `TraceScope`, а `TraceScopeResolverInterface` решает, что
считать «текущей единицей работы». Пакет биндит `ProcessTraceScopeResolver` — один
скоуп на процесс, как и нужно для FPM, `queue:work` и artisan, и как пакет вёл себя
всегда.

**Пакет не поставляет интеграций с рантаймами и ни об одном не знает.** Приложение,
работающее на конкурентном рантайме, переопределяет интерфейс своим резолвером:

```php
$this->app->singleton(
    \SLoggerLaravel\Traces\TraceScopeResolverInterface::class,
    fn() => new MyRuntimeScopeResolver()
);
```

Для рантайма на фиберах достаточно унаследоваться от `FiberTraceScopeResolver` и дать
только хранилище — где лежит скоуп корутины и как корутина видит скоуп той, что её
породила:

```php
class MyRuntimeScopeResolver extends \SLoggerLaravel\Traces\FiberTraceScopeResolver
{
    // скоуп, видимый из текущей корутины: свой либо ближайшего предка
    protected function read(): ?TraceScope
    {
        return MyRuntime::context()->find('slogger.trace_scope');
    }

    protected function write(TraceScope $scope): void
    {
        MyRuntime::context()->set('slogger.trace_scope', $scope);
    }
}
```

Само правило лежит в базовом классе, и у него две половины, обе важные: у корутины
**свой** стек (две корутины, снимающие с одного, закрывают трейсы друг друга), но
**родительский trace id наследуется** от той, что её породила, — поэтому вызов внутри
корутины цепляется к трейсу, который её запустил, а не приезжает сиротой.

**Профилирование внутри корутины отключается само.** XHProf процессный: он меряет всё,
что процесс делал между start и stop, а при конкурентном рантайме это все корутины,
успевшие поработать в промежутке, — и всё это припишется тому трейсу, который
остановился первым. Неверные числа хуже, чем их отсутствие, поэтому у трейсов,
запущенных внутри фибера, данных профилирования нет.

Ещё одно, что стоит знать: **батч трейсов общий**. Диспетчер буферизует трейсы на
процесс, поэтому один `SendTracesJob` может увезти трейсы нескольких корутин. Так и
задумано: батч — деталь транспорта, а родитель у каждого трейса свой.

## Профилирование (XHProf)

Только для трейсинга HTTP-клиента.

1) Установите расширение:

```bash
pecl install xhprof
```

2) Включите в `php.ini`:

```ini
[xhprof]
extension=xhprof.so
```

3) Включите:

```dotenv
SLOGGER_PROFILING_ENABLED=true
```

```bash
vendor/bin/phpunit
```

Конфигурация testbench использует in-memory sqlite и диспатчер `memory`.

## Диагностика проблем

- Диспатчер не стартует: проверьте `SLOGGER_ENABLED=true` и корректное имя диспатчера.
- Нет трейсов: убедитесь, что вотчеры включены, а middleware применён к запросам.
- Диспатчер queue не отправляет: проверьте воркеры очереди и URL API-клиента.
- Ошибки socket-клиента: проверьте адрес сокета и доступность бэкенда.
